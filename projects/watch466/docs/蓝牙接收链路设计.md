# 蓝牙接收链路设计

> 对应实现：[`functions/func_lunchbox_ble_app.c`](../functions/func_lunchbox_ble_app.c)
> 平台侧接口：[`platform/bsp/bsp_ble/app_blue_fit.c`](../../../platform/bsp/bsp_ble/app_blue_fit.c)
> 协议：[蓝牙通讯协议1.0.6.md](蓝牙通讯协议1.0.6.md)

---

## 1. 总览

主循环只有一个入口 `lunchbox_ble_process()`，饭盒协议从「取包」到「分发」全部在
`func_lunchbox_ble_app.c` 内完成，不再经过 `ble_app_process()` →
`ble_app_watch_process()` → `ble_app_blue_fit_rx_callback()` 那条老链路。

```
 手机 APP
    │  GATT Write (特征值 UUID ...ae03...)
    ▼
┌──────────────────────────────────────────────┐
│ 蓝牙中断上下文                                │
│ gatt_callback_app()          app_blue_fit.c  │  ← 平台代码，未改动
│   memcpy 到环形缓冲区 ble_cmd_cb              │
│   cmd_wptr++                                 │
└──────────────────────────────────────────────┘
    │  4 槽环形缓冲区，每槽 256 字节
    ▼
┌──────────────────────────────────────────────┐
│ 主循环上下文                                  │
│                                              │
│ §1 取包  lunchbox_ble_process()              │
│      ble_app_lunchbox_rx_pop() 一次取空       │
│                    ↓                          │
│ §2 组帧  lb_ble_stream_*()                   │
│      字节流 → 完整帧（帧头/长度/校验和）       │
│                    ↓                          │
│ §3 分发  lb_ble_dispatch() / lb_ble_on_*()   │
│      帧 → 业务（一个命令一个函数）             │
└──────────────────────────────────────────────┘
    │
    ├─→ 加热模块（UART 转发）
    ├─→ OTA（主单片机 / 加热模块）
    └─→ 本地应答（BLE Notify）
```

### 分层原则

三段**互不引用对方的内部状态**：

| 层 | 知道什么 | 不知道什么 |
|---|---|---|
| §1 取包 | 平台队列怎么取 | 帧长什么样、命令是什么 |
| §2 组帧 | 帧头 `0x55AA`、长度字段、校验和 | 命令字含义、业务规则 |
| §3 分发 | 命令字含义、业务规则 | 数据是怎么攒起来的、有没有分包 |

组帧层**不看命令字**，分发层**不碰缓冲区**。加一个新命令只动 §3，改传输方式只动 §1。

## 2. `lunchbox_ble_process()`

主循环每轮调用一次。

```c
void lunchbox_ble_process(void)
{
    for (;;) {
        lb_ble_stream_reserve(LB_BLE_RX_PKT_MAX);   // ① 腾空间
        u16 n = ble_app_lunchbox_rx_pop(ble_rx_buf + ble_rx_len,
                                        LB_BLE_RX_PKT_MAX);  // ② 取一包
        if (n == 0) break;                          // ③ 队列空 → 退出
        ble_rx_len += n;                            // ④ 累加
        ble_rx_tick = tick_get();                   // ⑤ 记录时刻
        lb_ble_stream_pump();                       // ⑥ 切帧 + 分发
    }
    lb_ble_stream_timeout();                        // ⑦ 残帧超时清理
}
```

### 关键设计点

**① 取包前先 reserve**
`rx_pop` 的 `cap` 参数是硬截断：尾部只剩 100 字节而包有 150 字节时，后 50 字节会被
丢弃，帧直接残废。所以每次取包前先保证尾部有一个整包（256 字节）的空间。

**② 直接取到重组缓冲区尾部**
不经过中间临时数组，省一次拷贝，也不在栈上开 256 字节数组。

**⑥ 每取一包就 pump**
不是取完所有包再统一切帧。这样单包内含多帧时能立即处理，缓冲区占用也更低。

**⑦ 超时检查在循环外**
残帧超时必须**每轮主循环都跑**，哪怕这轮一个包都没收到 —— "没有新数据进来"恰恰
是残帧卡住的场景。放在循环内会被 `n == 0` 的 `break` 跳过。

### 为什么是循环而不是取一包就走

生产者是蓝牙中断（快），消费者是 UI 主循环（一轮几十毫秒，慢）。一轮只消费一包时，
队列涨起来第 5 包就会覆盖第 1 包，静默丢帧。一轮取空消除了这个窗口。

**终止性**：环形缓冲区 4 个槽，正常最多 4 次迭代（加上取包期间中断新塞入的几包）。
BLE 到达速率（连接间隔几十毫秒一包）远低于消费速率，`rptr` 一定追得上 `wptr`。

**写成 `for(;;)+break` 的原因**：每次取包**前**必须先跑 `reserve`，条件表达式里塞不下。

## 3. 组帧层

### 缓冲区

```c
static u8  ble_rx_buf[512];  // 重组缓冲区
static u16 ble_rx_len;       // 有效字节数
static u32 ble_rx_tick;      // 最近一次写入时刻
```

**512 的来由**：要能同时装下「一个残帧 + 一个整包」。APP→MCU 最长的帧是 OTA 数据包
（`9 + 5 + 128 = 142` 字节），残帧最多 141 字节，加上单包上限 256，512 有充分余量。

### 切帧规则

`lb_ble_stream_pump()` 从缓冲区头部反复切帧：

| 情况 | 动作 |
|---|---|
| 前两字节不是 `0x55 0xAA` | 丢 1 字节，重新找帧头 |
| 长度字段异常（`9 + data_len > 512`） | 丢 1 字节，重新找帧头 |
| 数据没收齐（`ble_rx_len < total`） | **原地等待**下一个分包 |
| 校验和不符 | 丢 1 字节，重新找帧头 |
| 校验通过 | 打日志 → 分发 → 丢掉整帧 |

丢 1 字节而不是整块清空，是因为**真正的帧头可能就在这堆垃圾字节后面**，整块清空会
连累后面的好数据。

### 空间不足时丢最旧的

```c
static void lb_ble_stream_reserve(u16 need)
{
    u16 free_len = LB_BLE_RX_BUF_SIZE - ble_rx_len;
    if (free_len >= need) return;
    u16 drop = need - free_len;
    printf("BLE: rx buf full, drop %u stale bytes\n", drop);
    lb_ble_stream_drop(drop);      // 丢头部，不丢新数据
}
```

缓冲区里积到需要 reserve 的程度，说明头部那堆字节属于一个**已经不可能补齐的残帧**
（合法帧不会超过 512-256）。丢它，保住新来的好包。

### 残帧超时

```c
#define LB_BLE_FRAME_TIMEOUT_MS 3000
```

3 秒没等到后续分包就丢弃，防止半帧长期占着缓冲区头部。由主循环轮询触发。

### 帧数据的生命周期

```c
frame.data = ble_rx_buf + 8;   // 指向缓冲区内部
lb_ble_dispatch(&frame);       // 分发期间有效
lb_ble_stream_drop(total);     // ← 到这里 frame.data 失效
```

分发全程在主循环上下文，`ble_rx_buf` 只有这一个写者，分发过程中不会被改动。
分发链路（UART 发送、Flash 写入、BLE Notify）都不会反过来调用接收层，无重入风险。

## 4. 分发层

```c
static void lb_ble_dispatch(lb_rx_frame_t *rx)
{
    switch (rx->cmd) {
    case LB_CMD_PRODUCT_INFO:   lb_ble_on_product_info(rx);  break;  // 0x01
    case LB_CMD_STATUS_REPORT:  lb_ble_on_status_report(rx); break;  // 0x03
    case LB_CMD_OTA_START:                                           // 0x0c
    case LB_CMD_OTA_DATA:                                            // 0x0d
    case LB_CMD_OTA_END:        lb_ble_on_ota(rx);           break;  // 0x0e
    default:                    lb_ble_on_forward(rx);       break;  // 其余
    }
}
```

| 命令 | 处理 |
|---|---|
| `0x01` 产品信息 | 记录 APP 时间戳；透传加热模块，挂起等它的版本号回来再答复 APP；转发不成立则用本地缓存直接答复 |
| `0x03` 状态上报 | 只取 `dpid=11` 的权威时间戳，本地消化，**不转发**给加热模块 |
| `0x0c/0x0d/0x0e` OTA | 按 `target` 字段分流：`0x01`/缺省 → 主单片机，`0x02` → 加热模块 |
| 其余（`0x02`、`0x04`~`0x0a`） | 翻译成 UART 帧转发加热模块，应答由 UART 侧按 `msg_flag` 配对回传 |

`0x01` 是唯一直发 UART（`uart_bufs_tx`）而不进重试队列的命令 —— 与加热模块的应答
配对靠 `lb_product_info_pending`，排队会打乱 1 秒超时窗口。

## 5. 平台侧接口

```c
u16 ble_app_lunchbox_rx_pop(u8 *out, u16 cap);
```

平台侧唯一对外出口（[`app_blue_fit.c`](../../../platform/bsp/bsp_ble/app_blue_fit.c)）。

- **按 handle 判通道**：`handle == gatts_rx_base.handle` 才是饭盒数据。handle 由协议栈
  在注册特征值时分配、写入时原样回传，是链路层事实，不像"看前两字节是不是 55AA"
  那样需要靠状态记忆去猜分包。
- **拷贝而非返回槽内指针**：避免解析期间蓝牙中断覆写同一个槽。
- **非饭盒通道 `continue` 而非 `return`**：`gatt_callback_app` 也服务支付宝特征值
  （`SECURITY_PAY_EN` 打开时），遇到别的通道要跳过继续找，不能当成"队列空了"。

### 环形缓冲区

```c
#define BLE_CMD_BUF_LEN   4
#define BLE_CMD_BUF_MASK  (BLE_CMD_BUF_LEN - 1)
```

读写指针是**只增不减的 `u8` 计数器**，用 `& BLE_CMD_BUF_MASK` 折算成 `0~3` 的数组下标。
空判断靠 `cmd_rptr != cmd_wptr`，所以指针不能归零 —— 必须能"跑在前面"才有大小差。

`u8` 到 255 后溢出回 0，因为 256 是 4 的整数倍，回绕处下标序列仍然连续。

**容量必须是 2 的幂**，否则 `& MASK` 不等价于 `% LEN`。已加编译期断言。

## 6. 已知短板

| 问题 | 影响 | 状态 |
|---|---|---|
| 环形缓冲区无写满检查 | `gatt_callback_app` 无条件覆盖槽位，第 5 包盖掉第 1 包，静默丢帧无日志 | 未处理（需改动 `gatt_callback_app` 函数体） |
| `ble_cmd_cb.wakeup` 只写不读 | `ble_app_watch_need_wakeup()` 硬编码 `return false`，BLE 收到数据不会唤醒 GUI、不会阻止休眠 | 原有行为，未改动 |
| 接收热路径有 `printf` | 每帧打印整帧十六进制 + DataPoint 解析，串口阻塞。手机灌包时会拖慢主循环 | 保留，排查用；卡顿时可关掉帧日志 |
| `struct ble_cmd_t.len` 为 `u8` | `len == 256` 会截断成 0。当前 MTU=200 到不了，理论边界不严谨 | 未改动 |

## 7. 相比旧实现修掉的问题

| # | 旧实现 | 现在 |
|---|---|---|
| 1 | `BLE_CMD_BUF_LEN=6` 而掩码是 5，下标退化成 `0,1,0,1,4,5,4,5`，槽 2/3 永不使用，**第 3 包覆盖第 1 包** | 改为 4，掩码成立，实际深度 4 |
| 2 | 每轮主循环只取一包，生产快于消费 | 一轮取空 |
| 3 | 解析期间数据指针直指环形槽，中断可覆写 | 拷贝出来再解析 |
| 4 | 缓冲区满时把**新来的包**一起丢掉 | 只丢头部残帧字节 |
| 5 | 3 秒超时只在"有新数据到达"时判定，残帧可永久滞留 | 主循环轮询 |
| 6 | `9 + data_len` 用 `u16` 计算，`data_len` 接近 65535 时溢出绕过超长保护 | 用 `u32` |
| 7 | 重组**前**按 `data[4]` 当命令字打日志，分包时打印假信息 | 重组后按完整帧打印 |
| 8 | 路由靠"前两字节是 55AA 或 `rx_pending()`"猜通道 | 按 GATT handle 判 |
