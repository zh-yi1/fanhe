# 通信联调测试手册

按 T1→T7 顺序执行,每一步都只依赖前一步,出问题能立刻定位到层。
所有帧的校验和已算好,可直接复制发送。

代码对应关系:蓝牙来的帧进 [`lb_ble_dispatch()`](../functions/comm/lb_ble_app.c#L568),
串口来的帧进 [`lb_uart_on_frame()`](../functions/comm/lb_uart_app.c#L293)。

---

## 0. 准备

### 0.1 连接

- **蓝牙名** `AR0MA-NY_XXXX`（XXXX = MAC 后两字节,见开机日志)
- **写**(发命令) `0000ae03-0000-1000-8000-00805f9b34fb`
- **通知**(收应答) `0000ae04-0000-1000-8000-00805f9b34fb`
- 连上后**先订阅 ae04 的 Notify**,否则收不到任何应答
- 日志串口 **PB3 / 115200**;加热模块串口 **PB8(TX) PB9(RX) / 115200**

### 0.2 开机自检

这三条必须出现:

```
[MAC persist] loaded from flash: XX:XX:XX:XX:XX:XX
btstack config: BT[1]; BLE[1]
lb_link: init ok TX=PB8 RX=PB9 baud=115200
```

第一条给出本机 MAC(用来确认扫描时没连错设备),第二条说明蓝牙协议栈起来了,
第三条说明串口起来了。缺任何一条,后面都不用测。

### 0.3 日志前缀

| 前缀 | 含义 |
|:---|:---|
| `BLE==>RX[n]:` | 收到 APP 的帧 |
| `BLE==>TX [n]:` | 发给 APP |
| `BLE->UART==>TX[n]:` | 0x01 产品信息直发模块(不进转发队列) |
| `UART<==TX[n]:` | 发给模块 |
| `UART==>RX[n]:` | 收到模块的帧 |
| `UART->BLE[n]:` | 模块数据回传 APP |

> **按键通知帧(dpid=12)收发都不打印**,这是刻意跳过的,没日志不代表链路断了。
> 写了 ae03 却没有 `BLE==>RX` 时,把 [lb_ble_app.c:53](../functions/comm/lb_ble_app.c#L53)
> 的 `LB_BLE_CHUNK_LOG_EN` 改成 `1`,可看到每片到达的字节数。

### 0.4 时间相关的帧要重新生成

T5/T6/T7 的帧里含**当前时间戳**,本文档里的值是 `2026-07-29 17:40` 生成的。
隔天测请用第 8 节的脚本重新生成,否则预约会落在过去的时间。

## T1 蓝牙单边（不碰串口）

0x09/0x0a 是本机业务,完全不经过串口。**这一步通了 = 蓝牙收发、组帧、分发、应答全链路正常。**

| # | 测什么 | 协议 | 发送到 ae03 |
|:--:|:---|:---|:---|
| T1-1 | 查全部模式预设 | 蓝牙 §3.9 `0x09` | `55 AA 00 01 09 00 00 00 09` |
| T1-2 | 查模式2(鸡腿) | 蓝牙 §3.9 `0x09` | `55 AA 00 02 09 00 00 01 02 0D` |
| T1-3 | 改模式1为80℃/45min | 蓝牙 §3.10 `0x0a` | `55 AA 00 03 0A 00 00 03 01 04 2D 41` |

**期望**

- T1-1 → ae04 收到 `55 AA 00 01 09 00 00 09 01 03 1E 02 04 2D 03 05 14 83`
  (每 3 字节一条 `[模式,温度档,时长]`:1=70℃/30min,2=80℃/45min,3=90℃/20min)
- T1-2 → ae04 收到 `55 AA 00 02 09 00 00 03 02 04 2D 40`
- T1-3 → 日志 `mode preset local: id=1 temp=4 dur=45 min`,ae04 收到 `55 AA 00 03 0A 00 00 00 0C`,
  同时串口发出一条 msg_flag 为 `0x8x` 的预设同步帧
- **T1-3 之后重发 T1-1**,第一条应变成 `01 04 2D`

## T2 串口链路（什么都不用发）

模块会自己发东西,盯日志即可。

| 现象 | 协议 | 期望日志 |
|:---|:---|:---|
| 心跳 | MCU §6.1 `0x05` | `UART==>RX[10]` 紧跟 `UART<==TX[10]`,数据从 `00` 变 `01` |
| 分钟推送 | MCU §3.1 `0x01` + dpid=14 | 每 **60 秒**一条 `UART==>RX[68]`,含 `0E 02 00 04 xx xx xx xx` |

**心跳一问一答成对出现 = 串口收发双向完全打通。**

蓝牙已连时,模块的主动上报还会多一条 `UART->BLE[..]`,APP 收到 0x03 状态推送。

## T3 基础桥接

| 测什么 | 协议 | 发送到 ae03 |
|:---|:---|:---|
| 查设备动态属性 | 蓝牙 §3.2 `0x02` → MCU §3.1 `0x01` | `55 AA 00 10 02 00 00 00 11` |

**期望五行日志齐全**,这是桥接的完整闭环:

```
BLE==>RX      收到 APP 请求
UART<==TX     转发给模块(自动前置 DP11 时间戳 + DP01 开关)
UART==>RX     模块应答
UART->BLE     翻译回传
BLE==>TX      发给 APP
```

模块不应答时会看到重试和兜底,**这也是正确行为**:

```
lb_bridge: rsp timeout, retry 1/2 uart_cmd=0x01
lb_bridge: rsp timeout, retry 2/2 uart_cmd=0x01
lb_bridge: no rsp after 3 tries, reply APP err (ble_cmd=0x02)
```

## T4 加热控制

> ⚠️ **模块会真的加热**,测之前确认饭盒里没有不该加热的东西。

| # | 测什么 | 发送到 ae03 |
|:--:|:---|:---|
| T4-1 | 开始加热 自定义/70℃/30min | `55 AA 00 11 04 00 00 17 02 04 00 01 01 05 02 00 04 00 00 00 1E 07 04 00 01 03 0A 01 00 01 01 78` |
| T4-2 | 停止加热 | `55 AA 00 12 04 00 00 05 0A 01 00 01 00 26` |
| T4-3 | 关机(模式=关) | `55 AA 00 13 04 00 00 05 02 04 00 01 00 22` |

**期望**

- T4-1 → 模块应答里 `DP10: HeatEn=ON`、`DP06: Remain=30min`,之后剩余时间逐分钟递减
- T4-2 → `DP10: HeatEn=OFF`、`Remain=0min`
- T4-3 → 串口帧里会**自动补一条 `0A 01 00 01 00`**(APP 只发了模式关,桥补的停止加热信号)

## T5 时间同步

| 测什么 | 协议 | 发送到 ae03 |
|:---|:---|:---|
| 下发时间 | 蓝牙 §3.3 `0x03` + dpid=11 | `55 AA 00 20 03 00 00 08 0B 02 00 04 6A 69 CA 8A 62` |

**期望日志**

```
BLE: APP time sync via 0x03, ts=1785318026
timesync: sent to heat module, wait ack (ts=1785318026)
UART<==TX[22]: ...           ← msg_flag 是 0x8x 号段
UART==>RX[..]: ...           ← 模块应答
timesync: heat module acked, local time saved     ← 这条出现才算成功
```

只停在 `wait ack` = 模块没应答,本机时间**不保存**(刻意设计,保证两边一致)。

> **已知问题**:模块存进 RTC 的值会比下发值大 16 小时,见 §7。

## T6 产品信息

| 测什么 | 协议 | 发送到 ae03 |
|:---|:---|:---|
| 查产品信息 | 蓝牙 §3.1 `0x01` | `55 AA 00 21 01 00 00 04 6A 69 CA 8A 4C` |

这条**不进转发队列**:先直发模块查版本号,等 1 秒,拿到 dpid=13 后再回 APP。

**期望**:ae04 收到 **90 字节**(data_len=`0x51`=81),字段依次是

```
蓝牙名(16) 版本(8) 型号(10) MAC(6) SN(32) 颜色(1) 主MCU版本(4) 模块版本(4)
```

- 型号应为 `SF101`(`53 46 31 30 31`)、版本 `01.00.00`
- **最后 4 字节是模块真实版本号**,非零说明模块应答成功
- 模块 1 秒不回则日志 `product info: heat module no reply, use cached ver`,
  照样回 APP,但模块版本号是 0

## T7 预约全流程

按顺序发这六条,每一条的结果决定下一条。

| # | 测什么 | 协议 | 发送到 ae03 |
|:--:|:---|:---|:---|
| T7-1 | 新增预约 | 蓝牙 §3.6 `0x06` → MCU §3.6 `0x03` | `55 AA 00 30 06 00 00 29 01 74 65 73 74 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 6A 69 CC E2 03 1E 01 FF C1` |
| T7-2 | 查列表 | 蓝牙 §3.5 `0x05` → MCU §3.5 `0x02` | `55 AA 00 31 05 00 00 00 35` |
| T7-3 | 修改为80℃/45min | 蓝牙 §3.7 `0x07` → MCU §3.6 `0x03` | `55 AA 00 32 07 00 00 29 01 74 65 73 74 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 00 6A 69 CC E2 04 2D 01 FF D4` |
| T7-4 | 查列表 | `0x05` | `55 AA 00 33 05 00 00 00 37` |
| T7-5 | 删除 | 蓝牙 §3.8 `0x08` → MCU §3.6 `0x03` | `55 AA 00 34 08 00 00 01 01 3D` |
| T7-6 | 查列表 | `0x05` | `55 AA 00 35 05 00 00 00 39` |

**期望**

- **T7-1** 串口发出 **42 字节**数据(桥在前面插了 `预约mode` 字节 = `01` 自定义加热),
  模块回 `err=00`,数据区 1 字节是**模块分配的 ID**。
  ⚠️ **模块不采纳我们给的 ID,它自己分配**。如果返回的不是 `01`,后面 T7-3/T7-5 的 ID 要跟着改。
- **T7-2** 列表里应有 1 条,温度时长 `03`/`1E`
- **T7-3** 模块回 `err=00`。**修改和新增靠 ID 区分**——ID 已存在是改,不存在会新建一条
- **T7-4** 仍是 1 条,温度时长变成 `04`/`2D`
- **T7-5** 串口发出 **42 字节**(mode=`00` 表示删除 + ID,其余填 0),模块回 `err=00`
- **T7-6** 列表应为空

> 删除以前只发 2 字节 `[mode,id]`,模块返回 err=01;2026-07-29 已改为按协议发完整 42 字节。
> 这一步是验证该修复的重点。

## T8 OTA（暂缓)

需要固件包才能测:

- **加热模块升级**:模块厂提供的 `.bin`,**包头前 4 字节必须是 `11 22 33 44`**。
  流程:BLE 收 → 存 SPI Flash(0x3E0000) → 校验 CRC → 串口 128 字节一包推送 →
  模块重启进 bootloader(会有电压跌落,主板可能跟着复位,靠断电续传恢复)
- **主 MCU 升级**:本工程 `postbuild_ble_ota.bat` 生成的升级包

**先测加热模块的**(坏了只影响模块),主 MCU 的放最后,并留好重新烧录的手段。

## 7. 已知问题（不必重复上报）

### 加热模块固件侧

1. **RTC 时间 +16 小时** —— 下发 dpid=11 后,模块存进 RTC 的值比下发值大
   **57600 秒(正好 16 小时 = 8 小时时区的两倍)**,两次不同时间戳测试结果一致。
2. **预约时间丢日期** —— 下发完整 unix 秒,读回来变成 `unix % 86400`(当天秒数)。
   与第 1 条处理方式不一致(RTC 加偏移、预约取余)。
3. **每条命令回两遍** —— 同一帧连发两次,主板第一条当应答、第二条当主动上报,
   APP 每次操作会收到"命令应答 + 状态推送"两条相同内容。

### 主板侧(小瑕疵,不影响通信)

- 日志里 `version=01.00.00SF101` 串在一起 —— `version[8]` 存满没有结束符,
  `printf("%s")` 读进了后面的 `model`。线上字节是对的。

### 排错

| 日志 | 原因 |
|:---|:---|
| `BLE: checksum err, resync` | 校验和算错(从 `0x55` 起所有字节累加 % 256) |
| `BLE: bad data_len=` | 长度字段与实际数据字节数对不上 |
| `BLE: rx timeout, drop N` | 帧发了一半,3 秒没后续 |
| `lb_link: rx overflow` | 串口收太快,主循环没及时取走 |
| `lb_bridge: no rsp after 3 tries` | 模块 100ms×3 没应答,或应答 msg_flag 不匹配 |
| `UART: unknown cmd=0x..` | 模块发了 0x01~0x05 之外的命令字 |

## 8. 重新生成测试帧

改任何字节都要重算校验和,否则帧被静默丢弃、日志里什么都不出现。
msg_flag 用 `0x00~0x7F`(`0x80~0xFF` 是主板给模块发命令的号段)。

```python
import time

def frame(cmd, flag, data=b'', err=0):
    b = bytes([0x55,0xAA,0,flag,cmd,err,(len(data)>>8)&0xFF,len(data)&0xFF]) + data
    return b + bytes([sum(b) % 256])

def dpb(d,v): return bytes([d,1,0,1,v])                      # bool
def dpe(d,v): return bytes([d,4,0,1,v])                      # enum
def dpv(d,v): return bytes([d,2,0,4,(v>>24)&255,(v>>16)&255,(v>>8)&255,v&255])  # value
def sched(i,name,t,temp,dur,en,rep):                         # 41 字节预约结构
    return bytes([i]) + name.encode().ljust(32,b'\x00') + \
           bytes([(t>>24)&255,(t>>16)&255,(t>>8)&255,t&255,temp,dur,en,rep])

def hx(b): return ' '.join('%02X'%x for x in b)

now = int(time.time())
print('T5 时间同步  ', hx(frame(0x03, 0x20, dpv(11, now))))
print('T6 产品信息  ', hx(frame(0x01, 0x21, now.to_bytes(4,'big'))))
print('T7-1 新增预约', hx(frame(0x06, 0x30, sched(1,'test',now+600,3,30,1,0xFF))))
print('T7-3 修改预约', hx(frame(0x07, 0x32, sched(1,'test',now+600,4,45,1,0xFF))))
```

**常用 dpid**:1 总开关(bool) · 2 模式(enum,0关/1自定义/2鸡腿/3意面/4预约/5保温) ·
3 电量 · 5 时长(value,分) · 6 剩余(value,分) · 7 温度档(enum,0=40℃~6=100℃) ·
9 故障 · 10 是否加热(bool) · 11 APP时间戳 · 13 版本号 · 14 模块RTC时间

**命令字对照**(蓝牙 → 串口):

| 蓝牙 | 含义 | 转成串口 |
|:---:|:---|:---|
| `0x01` | 查产品信息 | `0x01`(直发,不进队列) |
| `0x02` | 查动态属性 | `0x01` |
| `0x03` | 状态上报 / 时间同步 | 不转发,只取 dpid=11 |
| `0x04` | 控制指令 | `0x01` |
| `0x05` | 查预约列表 | `0x02` |
| `0x06`/`0x07`/`0x08` | 新增/修改/删除预约 | `0x03`(靠 mode 和 ID 区分) |
| `0x09`/`0x0a` | 模式预设查/改 | **不转发**(本机数据);0x0a 额外同步一条 `0x01` |
| `0x0c`/`0x0d`/`0x0e` | OTA | `0x04` |
