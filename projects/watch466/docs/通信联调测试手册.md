# 通信联调测试手册（真实加热模块已接入）

按代码里两个分发函数的结构组织, 每一节对应一个 `case`, 照着发数据、照着看日志。

- 蓝牙来的帧 → [`lb_ble_dispatch()`](../functions/comm/lb_ble_app.c#L568) （lb_ble_app.c:568）
- 串口来的帧 → [`lb_uart_on_frame()`](../functions/comm/lb_uart_app.c#L293) （lb_uart_app.c:293）

---

## 0. 连接信息

- **蓝牙名**: `AR0MA-NY_XXXX`（XXXX = MAC 后两字节）
- **写**（你发命令）: `0000ae03-0000-1000-8000-00805f9b34fb`
- **通知**（设备回你）: `0000ae04-0000-1000-8000-00805f9b34fb`
- 连上后**先订阅 ae04 的 Notify**, 否则收不到应答。订阅成功日志: `BLE CCCD: ... cfg=1`
- 串口 115200 8N1, PB8=TX PB9=RX, 已接真实模块
- 开机日志应有 `lb_link: init ok TX=PB8 RX=PB9 baud=115200`

日志前缀:

| 前缀 | 含义 |
|:---|:---|
| `BLE==>RX[n]:` | 收到 APP 的帧 → 进 `lb_ble_dispatch` |
| `BLE==>TX [n]:` | 发给 APP |
| `BLE->UART==>TX[n]:` | 0x01 产品信息直发模块（不进转发队列）|
| `UART<==TX[n]:` | 发给模块 |
| `UART==>RX[n]:` | 收到模块的帧 → 进 `lb_uart_on_frame` |
| `UART->BLE[n]:` | 模块主动上报回推 APP |

> ⚠️ 模块是真的, **0x04 控制指令会真的启动/停止加热**。

# 第一部分: `lb_ble_dispatch()` —— APP 发过来的帧

函数在 [lb_ble_app.c:568](../functions/comm/lb_ble_app.c#L568), 一共 5 个分支。

## case 0x01 `LB_CMD_PRODUCT_INFO` — 查询产品信息

**协议**: 蓝牙 §3.1 → 处理函数 [`lb_ble_on_product_info()` :329](../functions/comm/lb_ble_app.c#L329)

这条**不进转发队列**, 流程特殊: 先把请求直发模块查版本号, 等模块 1 秒内应答,
拿到 dpid=13 后再回 APP; 模块不应答就用缓存版本号回。

**发送**（数据区 4 字节是 APP 时间戳）:
```
55 AA 00 04 01 00 00 04 6A 69 EB 40 06
```

**期望日志**:
```
BLE==>RX[13]: 55 AA 00 04 01 00 00 04 6A 69 EB 40 06
BLE->UART==>TX[29]: 55 AA 00 04 01 00 00 15 0B 02 00 04 6A 69 EB 40 01 01 00 01 01 0D 02 00 04 00 00 00 00 3F
UART==>RX[..]:  ← 模块应答, msg_flag 必须也是 04
timesync: via product info ack, local time saved
BLE==>TX [90]: ...   ← 81 字节设备信息
```

**判断**: ae04 收到 81 字节数据 = 蓝牙名(16)+版本(8)+型号(10)+MAC(6)+SN(32)+颜色(1)+主MCU版本(4)+**模块版本(4)**。
最后 4 字节非零 → 模块应答成功。

**模块不应答**时 1 秒后:
```
product info: heat module no reply, use cached ver
```
照样回 APP, 但模块版本号是 0。**这时时间也不会保存**（见下面 0x03）。

## case 0x03 `LB_CMD_STATUS_REPORT` — 时间同步

**协议**: 蓝牙 §3.3 + dpid=11 → 处理函数 [`lb_ble_on_status_report()` :378](../functions/comm/lb_ble_app.c#L378)

APP 方向只用来接收权威时间戳。**时间先发给模块, 模块应答后才保存本机** ——
这是刻意设计, 保证本机和模块时间一致。

**发送**（时间戳 `6A69EB40` = 2026-07-29 12:00:00 UTC）:
```
55 AA 00 0A 03 00 00 08 0B 02 00 04 6A 69 EB 40 23
```

**期望日志**:
```
BLE==>RX[17]: ...
BLE: APP time sync via 0x03, ts=1785326400
timesync: sent to heat module, wait ack (ts=1785326400)
UART<==TX[..]: ...          ← 发给模块
UART==>RX[..]: ...          ← 模块应答
timesync: heat module acked, local time saved     ← 这条出现才算成功
```

**判断**: 必须看到最后一条 `local time saved`。只停在 `wait ack` = 模块没应答, 本机时间**没保存**（正常设计, 不是 bug）。

## case 0x02/0x04/0x05/0x06/0x07/0x08 — 纯转发

**处理函数**: [`lb_ble_on_forward()` :548](../functions/comm/lb_ble_app.c#L548)

这 6 条走同一条路: 翻译成 UART 帧 → 进转发队列（一发一收, 100ms 超时 ×3 次重试）
→ 模块应答后自动翻译回传 APP。

| BLE 命令 | 协议 | 转成串口 | 说明 |
|:---:|:---|:---:|:---|
| `0x02` | §3.2 查动态属性 | MCU `0x01` | 前置 DP11 时间戳 + DP1 开关 |
| `0x04` | §3.4 控制指令 | MCU `0x01` | 前置 DP11 时间戳 |
| `0x05` | §3.5 查预约列表 | MCU `0x02` | 无数据, 模块多帧应答 |
| `0x06` | §3.6 新增预约 | MCU `0x03` | 41B → 42B（前插 action）|
| `0x07` | §3.7 修改预约 | MCU `0x03` | 同上 |
| `0x08` | §3.8 删除预约 | MCU `0x03` | 只发 2B `[action,id]` |

### 测试帧

| 测什么 | 发送到 ae03 | 判断 |
|:---|:---|:---|
| 查动态属性 | `55 AA 00 06 02 00 00 00 07` | ae04 收到 0x02 应答, 内容是模块真实状态 |
| **开始加热** 70℃/30min | `55 AA 00 07 04 00 00 17 02 04 00 01 01 05 02 00 04 00 00 00 1E 07 04 00 01 03 0A 01 00 01 01 6E` | 模块**真的加热**, 之后陆续收到剩余时间递减的上报 |
| **停止加热** | `55 AA 00 08 04 00 00 05 0A 01 00 01 00 1C` | 模块停止 |
| 关机（模式=关） | `55 AA 00 09 04 00 00 05 02 04 00 01 00 18` | 串口帧里**自动补了 `0A 01 00 01 00`** |
| 查预约列表 | `55 AA 00 0B 05 00 00 00 0F` | 模块多帧应答, 等 seq>=total 后回传 |

**完整日志链条**（五行都要有）:
```
BLE==>RX      收到 APP 请求
UART<==TX     转发给模块
UART==>RX     模块应答
UART->BLE     翻译回传
BLE==>TX      发给 APP
```

**模块不应答**时:
```
lb_bridge: rsp timeout, retry 1/2 uart_cmd=0x01
lb_bridge: rsp timeout, retry 2/2 uart_cmd=0x01
lb_bridge: no rsp after 3 tries, reply APP err (ble_cmd=0x02)
```
给 APP 回 err=0x01。**这本身是正确行为**, 说明重试兜底正常。

## case 0x09 `LB_CMD_MODE_QUERY` — 查模式预设

**协议**: 蓝牙 §3.9 → 处理函数 [`lb_ble_on_mode_query()` :449](../functions/comm/lb_ble_app.c#L449)

**本机预设表, 完全不碰串口**。所以这条是验证蓝牙链路的最佳首选 ——
通了就说明 BLE 收 + 组帧 + 分发 + 应答 + BLE 发 全链路正常。

| 发送 | 判断 |
|:---|:---|
| `55 AA 00 01 09 00 00 00 09`（查全部）| ae04 收到 `55 AA 00 01 09 00 00 09 01 03 1E 02 04 2D 03 05 14 83` |
| `55 AA 00 02 09 00 00 01 02 0D`（只查模式2）| ae04 收到 `55 AA 00 02 09 00 00 03 02 04 2D 40` |

应答每 3 字节一条 `[模式, 温度档, 时长分钟]`, 默认: 1=70℃/30min, 2=80℃/45min, 3=90℃/20min。

## case 0x0a `LB_CMD_MODE_MODIFY` — 改模式预设

**协议**: 蓝牙 §3.10 → 处理函数 [`lb_ble_on_mode_modify()` :476](../functions/comm/lb_ble_app.c#L476)

改本机表 **+ 额外发一条 MCU `0x01` 同步给模块**（`lb_heat_cmd_mode_preset`）。

**发送**（模式1 → 80℃/45min）:
```
55 AA 00 03 0A 00 00 03 01 04 2D 41
```

**期望日志**:
```
BLE==>RX[12]: ...
mode preset local: id=1 temp=4 dur=45 min
UART<==TX[..]: ...        ← 同步给模块, msg_flag 是 0x80+ 号段
BLE==>TX [9]: 55 AA 00 03 0A 00 00 00 0C
```

**判断**: 再发一次 0x09 查询, 第一条应该变成 `01 04 2D`。

> **这条要重点观察模块反应**: MCU 协议没有专门的"预设"命令, 移植时是用 0x01 属性帧
> 承载 DP2(模式)+DP7(温度)+DP5(时长)、**故意不带 DP10(是否加热)** 来表达"只改预设不启动"。
> 确认模块收到后不会误开始加热。

模式号只允许 1~3, 越界返回 err=0x01。

# 第二部分: `lb_uart_on_frame()` —— 模块发过来的帧

函数在 [lb_uart_app.c:293](../functions/comm/lb_uart_app.c#L293)。

**进 switch 之前先做一件事**: [`lb_bridge_on_response()` :307](../functions/comm/lb_uart_app.c#L307)
判断这帧是不是"某条 APP 转发请求的应答"（靠 msg_flag 配对）。是的话就翻译回传 APP,
并标记 `consumed`。**这一步和下面的本地业务不互斥**, 两边都会执行。

## case 0x01 `LB_UART_CMD_DYNAMIC` — 动态属性（最重要）

[lb_uart_app.c:310](../functions/comm/lb_uart_app.c#L310) · **协议 MCU §3.1**

模块的状态上报和查询应答合并在这一条里, 代码里按顺序做 4 件事:

| 顺序 | 做什么 | 对应日志 |
|:--:|:---|:---|
| 1 | 扫 **dpid=14** → 有的话同步本机时间 | 无专门日志, 看 DP 解析里有没有 `0E` |
| 2 | `lb_ble_timesync_on_heat_frame()` 配对时间同步 | `timesync: heat module acked, local time saved` |
| 3 | `lb_ble_product_info_on_heat_frame()` 配对产品信息查询 | `timesync: via product info ack` + 回 APP 81 字节 |
| 4 | `lb_ui_state_feed_dp()` 更新状态镜像（给 UI 用）| 无日志 |
| 5 | **都没认领** → 当作模块主动上报, 翻译成 BLE `0x03` 推 APP | `UART->BLE[n]:` |

**不用发任何东西**, 模块自己会来。盯日志:

| 现象 | 期望 | 说明 |
|:---|:---|:---|
| 每分钟推时间 | `UART==>RX[17]` 里含 `0E 02 00 04 xx xx xx xx` | dpid=14, 本机时间跟随 |
| 面板操作/状态变化 | `UART==>RX[..]` + `UART->BLE[..]`（蓝牙已连时）| 主动上报 |

**判断**: 有 `UART==>RX` = 串口收 + 解析正常。

> ⚠️ **模块每分钟推时间到底推不推, 是这次联调必须确认的第一件事**。不推的话本机时间
> 只在 APP 同步那一刻准确, 之后会漂。

## case 0x05 `LB_UART_CMD_HEARTBEAT` — 心跳

[lb_uart_app.c:356](../functions/comm/lb_uart_app.c#L356) · **协议 MCU §6.1**

收到数据区 `00`（请求）就回 `01`（应答）, msg_flag 原样回显。**固件自动完成, 不依赖任何业务逻辑。**

**期望日志**（一问一答成对出现）:
```
UART==>RX[10]: 55 AA 00 xx 05 00 00 01 00 ..
UART<==TX[10]: 55 AA 00 xx 05 00 00 01 01 ..
```

**判断**: 这一对出现 = **串口收发双向完全打通**, 是最干净的串口验证点。
不应答的话模块会报"蓝牙模组心跳超时"故障（dpid=9）。

# 附: 排错

| 日志 | 原因 |
|:---|:---|
| `BLE: checksum err, resync` | 校验和算错 |
| `BLE: bad data_len=` | 长度字段和实际数据字节数对不上 |
| `BLE: rx timeout, drop N` | 帧发了一半, 3 秒没后续 |
| `lb_link: rx overflow` | 串口收太快, 主循环没及时取走 |
| `lb_bridge: queue full, drop ble_cmd=` | 转发队列满（深度 4）|
| 写了 ae03 但没有 `BLE==>RX` | 写错特征值; 或校验和错被静默丢弃 |

**两个会让你误判的地方**:

1. **按键通知帧(dpid=12)收发都不打印日志** —— [lb_uart_app.c:296](../functions/comm/lb_uart_app.c#L296)
   和 TX 侧都用 `lb_data_is_key_notify()` 刻意跳过了（太频繁）。按模块按键没日志属正常。
2. **BLE 分片日志默认关闭** —— 写了 ae03 但 `BLE==>RX` 不出现时, 把
   [lb_ble_app.c:53](../functions/comm/lb_ble_app.c#L53) 的 `LB_BLE_CHUNK_LOG_EN`
   改成 `1`, 能看到每片到达的字节数, 区分"没收到"和"收到了但组不成帧"。

**改数据要重算校验和**（从 `0x55` 起所有字节累加 % 256）, 否则帧被静默丢弃:

```python
def frame(cmd, flag, data=b'', err=0):
    body = bytes([0x55,0xAA,0x00,flag,cmd,err,(len(data)>>8)&0xFF,len(data)&0xFF])+data
    return body + bytes([sum(body) % 256])

def dp_bool(dpid,v): return bytes([dpid,0x01,0x00,0x01,v])
def dp_enum(dpid,v): return bytes([dpid,0x04,0x00,0x01,v])
def dp_val(dpid,v):  return bytes([dpid,0x02,0x00,0x04,(v>>24)&0xFF,(v>>16)&0xFF,(v>>8)&0xFF,v&0xFF])

f = frame(0x04, 0x07, dp_enum(2,1)+dp_val(5,30)+dp_enum(7,3)+dp_bool(10,1))
print(' '.join('%02X'%b for b in f))
```

msg_flag 用 `0x00~0x7F`（`0x80~0xFF` 是 MCU 给模块发命令的号段, [lb_heat_cmd.c:13](../functions/comm/lb_heat_cmd.c#L13)）。

常用 dpid: 1总开关(bool) 2模式(enum,0关/1自定义/2鸡腿/3意面/4预约/5保温) 3电量 5时长(value,分)
6剩余(value,分) 7温度档(enum,0=40℃~6=100℃) 9故障 10是否加热(bool) 11APP时间戳 13版本号 14模块RTC时间

**两处与协议文档字面不一致**（沿用 elunchbox 实机行为, 联调时确认模块接受）:
删除预约 `0x08` 串口侧只发 2 字节而非文档的 42 字节结构体; `0x07`/`0x08` 的 BLE 应答带模块回的 1 字节数据而文档写无数据。
