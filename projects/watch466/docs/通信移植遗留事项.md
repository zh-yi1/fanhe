### 1.4 加热模块固件待修（已反馈,非本机代码问题）

1. **RTC 时间 +16 小时**:主板下发 dpid=11 后,模块存进 RTC 的值比下发值大
   **57600 秒(正好 16 小时 = 8 小时时区的两倍)**,两次不同时间戳测试结果一致,
   疑似时区偏移加了两遍。
2. **预约时间丢日期**:下发预约 time=1785317795(完整 unix 秒),读回来变成
   **34595**,即 `unix % 86400`(当天秒数)。协议字段写的是 unix 秒。
   与第 1 条不一致(RTC 加偏移、预约取余),模块内部时间处理需统一。
3. **每条命令回两遍**:同一帧连发两次,主板第一条当应答、第二条当主动上报,
   导致 APP 每次操作收到"命令应答 + 状态推送"两条相同内容。需告知 APP 端。
4. **插电唤醒进黑屏充电页 —— 挂起,先不改**(2026-07-30 二次实测后维持)。
   实测(带括号打印固件,两次复现一致):深睡中插电 → 主板 **`WKUP reset`
   冷启动**(ROM 横幅确认,不是 WDT/软复位;RAM 全清,醒因闩锁/唤醒观察窗
   都不存在了)→ `func_run` 时 `CHARGE_DC_IN()` 未就绪没进黑屏页 → 正常
   开机:进主页 + 自动 power_on 把模块拍开。模块在 power_on 应答里报了
   DP4=1,但冷启动路径无人消费。
   **结论:模块侧发什么指令都救不了这条路** —— 板子是被复位重启的,不是
   深睡里被串口叫醒的,`lb_wake_apply()` 那套(含醒后主动查询)全不参与。
   要修只能走主板方案①:**开机后短观察窗(约 5s),`charging_now()`(含
   DP4)命中且无用户操作 → 关模块 → 落黑屏页**,顺带覆盖"冷启动插线但
   DC 检测未就绪"。方案②(`is_guioff` 守卫)针对的"唤醒建 form 撞 GPU"
   与本场景无关,仍备查。
   另:一次实测中模块 power_on 应答报 Charge=1,2s 后主动上报又变 0
   (若非"插了就拔"就是模块充电检测抖动)—— 做方案①前需模块侧确认,
   判据抖动会导致黑屏页进错/漏进。

### 2.2 预约:屏幕只能新增(设计决定,非缺口)

屏幕侧**只提供新增**,不做列表展示、不做修改、不做删除 —— 改和删只走 APP
(蓝牙 0x07/0x08 经桥转 UART 0x03)。

- 新增路径:预约键 → 预约时间页(时:分:秒滚轮)→ `new_ui_appointment_set()`
  暂存 → 加热设置页选温度/时长 → 确认时 `new_ui_appointment_take()` 命中
  → `lb_heat_cmd_schedule_set()`,回首页。同一个加热设置页,没暂存时走
  `lb_heat_cmd_start()` 立即加热。
- ID 由本机分配:`lb_ui_schedule_alloc_id()` 按列表镜像挑 1~12 最小空闲值,
  所以预约页 `enter()` 里必须先 `lb_ui_schedules_refresh()`。满 12 条丢弃并打日志。
- 下发参数固定 `enabled=1`、`repeat=0`(单次)、`name=NULL`(页面无输入项)。
- `lb_heat_cmd_schedule_delete()` 因此没有本机调用点,保留给将来/调试用。

### 2.4 开关机时序(2026-07-30 真机联调通过)

状态机在 `lb_uart_app.c`,一发一等,超时 500ms 也推进。

- **开机**:上电 500ms 后自动 `power_on(DP1=1)` → 应答 → 查预约列表 → IDLE。
- **关机**:`heat_off(DP10=0)` → 应答 → `power_off(DP1=0)` → 应答 → `OFF_DONE`
  → `func.c` 的 `lb_shutdown_seq_apply()` 取走边沿 → **manual_off 超低功耗深睡**
  (和长按 TCH5 3s 落地方式一致,不走 `FUNC_PWROFF` —— 那条路充电时
  `func_pwroff()` 会 return 不断电,会反复进关机页)。
- 入口三个,都汇到 `lunchbox_shutdown_start()`:APP 下发 0x04 带 DP1=0
  (`lb_ble_app.c` 拦截,每步应答各回 APP 一条);本机长按 TCH5 3s
  (`func_key.c`,原来是直接深睡、不通知模块,已改为走时序);
  **5 分钟无操作自动关机**(`func_lowpwr.c` 的 `sleep_process`,2026-07-30 改:
  原来 idle 到点只是息屏、再走"30s + bt_is_allow_sleep"的旧深睡机制,实测被
  模块心跳反复吵醒且被 BT 状态卡住睡不下去;现在直接走关机时序这条已验证的路。
  加热/保温/OTA 中不触发;黑屏充电页不重复触发;BLE 连着但无操作**也会**关机)。
- OTA 中由 `lunchbox_shutdown_blocked()` 拦下,APP 会收到 `ERR_EXEC_FAIL`。
- **充电不拦关机(2026-07-30 改)**:时序照跑(停加热+关模块),落地分流 ——
  未充电 → manual_off 深睡(真关机);充电中 → **黑屏充电页 FUNC_BLACK_SCREEN**,
  与真关机唯一区别是主板不深睡、还收串口状态(模块充电时仍上报 DP4 驱动动画)。
  黑屏页只认开关键短按(补跑 `lunchbox_boot_seq_kick()` 后进主界面),
  拔线去抖 2s 重走关机时序落深睡;强制跳页在该页冻结(边沿留着开机后生效)。
  冷启动时就插着线 → `func_run` 直接进黑屏页,并 `lunchbox_boot_seq_cancel()`
  撤销自动 power_on,模块保持关。
- **深睡唤醒(2026-07-30 二改)**:manual_off 唤醒**不重启**(RAM 原地复活),
  唤醒源只有 PE1(TCH5,持续 2s) 和 PB9(串口)。**任何串口指令都唤醒** ——
  曾做过"睡眠循环里偷听判帧,无关帧继续睡"(`lunchbox_wake_probe`),
  实测睡眠上下文收帧不完整("加热中和充电中指令收不全"),已回退删除。
  醒因闩锁(KEY/UART)在深睡循环置入,醒来后 `func.c` 的 `lb_wake_apply()`
  落页:KEY → `boot_seq_kick()` 进主界面;UART → **主动发状态查询**
  (`lb_heat_cmd_status_query()`,0x01 只带 DP11 时间戳 —— 不带 DP1:
  带 1 会把关着的模块拍开机,带 0 可能停掉预约到点正跑的加热),
  开 3s 观察窗等应答刷进状态镜像后判 —— 充电 → 黑屏充电页,
  加热 → 加热页,都不是(心跳等)→ 留在原页,靠 5min 无操作自动关机
  兜底重新睡回去;窗内 1s 没等到判据再补发一次查询。
  之所以主动查:唤醒那一帧本身常因 UART 起得慢收残,不能靠它判醒因。
  模块侧已确认:不带 DP1 的 0x01 查询帧,模块会**全量字段应答**。
  模块关(DP1=0)后还发不发心跳、充电时会不会主动上报、预约到点还执不执行,
  仍是模块固件行为,待联调确认。

  ④结果(`func_home_page.c` process):
  YES → `lb_lid_confirm_yes()`: 没停过 → 模块本来就在跑, 直接跳页
  (保温→保温页, enter 见模块在保温不会重发/清计时; 加热→加热页);
  超时停过 → 先 `lb_heat_cmd_resume(模式,温度,总时长,剩余)`(带 DP5+DP6,
  **模块侧需确认认不认控制方向的 DP6**)续跑再进加热页。
  NO → `lb_lid_confirm_no()` 立即停加热, 留主界面。
  resume 验证法:模块应答恒为全量字段(已确认), 发 resume 后看应答 ——
  DP6=下发的剩余值即认了; DP6 被重置成 DP5 即忽略了, 需模块侧支持。
  弹窗决策期间 `lb_ui_route_apply()` 把边沿取走丢弃(停止产生的回首页边沿、
  续跑产生的加热边沿都不能抢页)。首帧判定天然排除"开机几秒后预约到点
  新起的加热"(那种走正常路由进加热页)。插线冷启动走黑屏页分支不进等待;
  深睡唤醒不重启不过 func_run, 不会再弹。
- **黑屏充电页开机 = 长按 TCH5 3s**(2026-07-30 改,原来短按就开):
  在 `func_key_handle_pwr_long` 统一处理 —— 该页上 3s 到点的语义从"关机"
  换成"开机"(`boot_seq_kick` + 进主界面),页面本身不再处理任何按键。

联调时踩的两个坑:

1. **`OFF_DONE` 曾是死状态** —— 清它的只有 `lunchbox_shutdown_abort()`,而它
   零调用点。结果第一次关机跑完卡在 `OFF_DONE`,后续所有关机请求被
   `lunchbox_shutdown_start()` 的早退分支静默吃掉(连 APP 应答都不回),
   同时 `!is_done()` 恒假导致退出加热页不再停止加热。
   改为 `lunchbox_shutdown_done_take()` 一次性取边沿、取走即回 IDLE。
2. **关机第一步误用 `lb_heat_cmd_stop()`** —— 它是 `DP10=0` + **`DP1=1`**
   (给"停加热但不关机"用的,退出加热页就该这样),用在关机第一步等于断电前
   把总开关又打开一下,日志里能看到模块应答回 `PowerSwitch=ON`。
   已新增只发 `DP10=0` 的 `lb_heat_cmd_heat_off()` 给时序用。

### 2.5 已知 bug,暂缓修(2026-07-30 首次编译通过后发现)

编译 0 error,以下三条从警告里查出来,都不影响链接,按优先级排:

1. ~~**鸡腿/意面页温度显示成 `%F`**~~ — 已修(2026-07-30):两处 `"%%uF"` 改 `"%uF"`。

2. **保温预设时长存不下 1440** — 要先定方案。
   `lb_mode_preset_t.duration_min` 是 `u8`,`[LB_MODE_WARM] = { 5, 1440 }`
   实际存进去是 **160**(`1440 & 0xFF`)。告警
   `changed value from '1440' to '160'`。

   保温页本身不受影响(它用常量 `LB_WARM_DURATION_MIN`,不读预设表),
   但 APP 发 `0x09` 查保温预设会读到 160 分钟。

   **扩字段解决不了**:协议 `0x09/0x0a` 的时长字段就是 1 字节(上限 255),
   24 小时无法用这两条命令表达。两条路:
   - 保温那行填 `0`(协议 0 = 不限时),注释说明实际时长由
     `LB_WARM_DURATION_MIN` 决定、不走协议
   - 或协议加宽时长字段(需 APP 配合)

3. **`char buf[8]` 可能截断** — 低风险。
   `func_heat_page.c` 的 `"%uH%02uMin"`:120 分钟 → `"2H00Min"` 正好 7+1=8 不溢出;
   若哪天该页显示到 1440 分钟 → `"24H00Min"` 需要 9 字节,会被截成 `"24H00Mi"`。
   当前保温走保温页所以碰不到。buf 开到 16 即可。
