### 1.2 蓝牙/串口联调(进行中)
基本链路自检点:

| 环节 | 位置 | 检查方法 |
|:---|:---|:---|
| UART1 初始化 | `main.c` → `lunchbox_uart_init(LB_BAUD)` | 115200 8N1, TX=PB8, RX=PB9 |
| 串口收包 | `lb_uart_link.c` ISR → 环形缓冲 | `lb_link_rx_overflow()` 应恒为 0 |
| 串口解析 | `func.c` 主循环 → `lunchbox_uart_process()` | 收到帧有日志打印 |
| 心跳 | 模块发 0x05 → 自动应答 | 最简单的通路验证 |
| BLE 收包 | `app_blue_fit.c` 4 槽环形缓冲 → `lunchbox_ble_process()` | UUID ae30/ae03/ae04 |
| BLE 应答 | APP 发 0x01 查产品信息 | 会先透传模块查版本号,模块无应答则 1s 超时后仍回 APP |
| 桥接转发 | APP 发 0x04 控制 → UART 0x01 | 一发一收队列,100ms×3 重试 |

### 1.3 上板需重点验证的移植假设
这些是移植时做的设计假设,协议文档没有明确背书,需要真机确认:

1. **模式预设同步**:MCU 协议没有专门的预设命令,`lb_heat_cmd_mode_preset()` 用
   0x01 属性帧 DP2(模式)+DP7(温度)+DP5(时长)、**不带 DP10(开关)** 下发。
   确认模块收到后只更新预设、不会误触发启动/停止。
2. **dpid=14 分钟推送**:本机时间跟随依赖模块每分钟经 dpid=14 推 RTC 时间,
   确认模块固件确实会推;不推则本机时间只在 APP 同步那一刻准确。
3. **时间同步链**:APP 下发时间(0x03 dp11)→ 先转发模块 → 模块应答后才
   `lb_time_set_synced()` 保存本机。确认模块对该帧有应答,否则本机永远不保存时间。
4. **桥接的两处与文档字面不一致**(沿用 elunchbox 实机行为,文档未改):
   - 0x08 删除预约:UART 侧只发 2 字节 `[action, id]`(文档写 42B 结构体);
   - 0x07/0x08 的 BLE 应答带模块回的 1 字节数据(文档写无数据)。
5. **加热模块 OTA**:断电续传(SPI Flash 0x3E0000 元数据)、BLE 重连后补报结果,
   流程复杂,需完整走一遍升级。
